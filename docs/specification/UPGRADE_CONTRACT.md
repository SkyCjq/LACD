# LACD 升级契约：依赖、工作流锁定、升级、回退、兼容性（v1.0 冻结版）

> 状态：FROZEN（2026-10-12）。**本契约是 v1.0 硬门槛，不得延期。**

## 1. 维护责任边界

| 方 | 负责 |
|---|---|
| LACD 上游仓库 | 核心代码、标准契约、通用安全策略、可复用工作流、CLI、模板、测试、版本发布 |
| 采用者仓库 | 自己锁定的 LACD 版本、业务代码、项目专属规则、PR 审批 |

**禁止**：人工复制上游核心源码到各项目分别维护；在多个采用者仓库
分别修复同一个 LACD 缺陷；采用 `main`/浮动标签后未经审查自动获得安全策略变化。

**允许**：采用项目只保留最小托管集成入口、锁定记录、可审计的项目扩展；
必要的本地工作流/指令模板通过受控迁移更新。

## 2. 单一可信版本锁

采用者仓库的 `.lacd/lock.json`（锁格式版本独立，当前 "1"）必须记录：

- LACD CLI/发行包**精确版本**（如 `1.0.0`，不许 `v1`/`latest`/`main`）。
- 可信来源：`git-tag`（repo+ref+commit）/ `git-commit` / `local-dir`。
- 发布制品摘要（template bundle sha256，可用时）。
- 使用中的 Schema 版本与治理策略版本。
- 模板来源版本、受管文件列表及内容 sha256。
- GitHub 可复用工作流的**完整 commit SHA**（如用该模式），或本地工作流
  模板与预期摘要。

**标签本身不等于不可变安全保证。** 签名/证明为加分项；v1.0 不依赖
尚未实现的签名基础设施，也不伪称已验证。

`lacd status` 必须检测运行 CLI 版本与项目锁版本不一致并给出明确原因；
多项目锁定不同版本时提供项目隔离执行方案（本地 venv / 版本固定的
临时运行器），不靠全局安装碰运气。

## 3. 五类版本的兼容性关系

| 版本 | 标识位置 | 兼容性承诺 |
|---|---|---|
| CLI/发行包 | `lacd --version` / lock | SemVer；patch 兼容，minor 向后兼容，major 需迁移 |
| 配置 Schema | `lacd.yaml: schema_version` | "1"；新 Schema 大版本要求 CLI 同步升级 |
| 治理策略 | `lacd.policy_version` / lock | 策略版本升级不静默放宽规则（只允许收紧或等价） |
| 模板 | `template_version` / lock | 随 CLI 版本发布；跨 minor/major 走迁移引擎 |
| 锁格式 | `lock_format_version` | "1"；CLI 必须能读旧锁（必要时迁移并记录） |

不能仅靠版本号大小猜测兼容性；`upgrade --check` 必须报告每项的兼容性结论。

## 4. 升级发现

`lacd upgrade --check` 从**明确的可信上游来源**（默认 `SkyOneBranch/LACD` 的
GitHub Releases；可配置；测试可用 `file://` 本地源）查询版本，识别：

- 是否存在可用版本、是否在支持范围、Patch/Minor/Major 分类、升级前置条件。
- 网络失败 / 元数据非法 / 权限不足 → `UNVERIFIED` 或明确错误，
  **绝不**报告"已经最新"。
- 合理超时（默认 15s）、离线诊断、可理解的错误信息。
- 不得下载后直接执行未经验证的远端脚本。
- 不得构建未经 Human 授权就自动跟随最新版本的更新通道。

## 5. 升级策略（SemVer）

- **Patch**：默认适合生成常规升级 PR；仍必须测试 + Human 合并。
- **Minor**：可提升级 PR；检查新增字段/能力与受影响的治理规则。
- **Major**：需要显式迁移计划、兼容性诊断与 Human 审查；
  不得自动套用破坏性变更（`--to` 跨 major 必须 `--accept-major`）。
- **安全紧急更新**：优先通知并生成 PR，**不得绕过** Required Checks、
  CODEOWNERS 或 Human 合并。
- 允许采用者长期锁定旧版本；版本不受支持或有已知风险时**报告**，
  不在无授权时强制修改。

## 6. 幂等迁移、三方比较、防覆盖

`lacd upgrade --dry-run` 列出全部拟变更、风险等级、兼容性、人工审核点，
**不修改工作树**。

实际迁移区分三类内容并采用**三方比较**
（旧版上游基线＝锁中 hash ＋ 当前项目内容 ＋ 新版上游目标）：

1. **Upstream-owned**：锁中 hash 未变 → 用新版替换；变过 → 冲突。
2. **Project-owned**：永不触碰。
3. **Shared/merged**（如 AGENTS.md）：仅替换 LACD 受管标记 section，
   保留用户其余内容。

任何冲突明确呈现，**不得静默覆盖用户改动、删除项目原有检查、
放宽安全规则**。失败后工作树不得留在无法解释的半迁移状态：
预检 → 变更清单 → 备份 → 应用 → 失败回滚。

正常 `upgrade` 幂等：升级后再次执行同一目标版本无非预期 diff。

## 7. 升级 PR（`--prepare-pr`，显式触发）

1. 读锁定版本与目标版本；2. 检查可信源与兼容性；
3. 生成升级分支（`lacd/upgrade-to-<version>`），**不直接推受保护默认分支**；
4. 更新依赖锁、模板、固定工作流 SHA；
5. 生成可审计变更摘要（版本差异/迁移项/风险分级/测试计划/未解决冲突/人工检查点）；
6. 有权限且明确触发时创建/更新升级 PR；无权限时生成本地 patch + 人工步骤；
7. 检测重复升级 PR，避免重复提交；
8. 运行适用自动化验证并记录绑定 HEAD SHA；
9. **永不自动合并。**

定期提醒/自动建待审 PR 允许，但不能暗中安装、写默认分支或改远端管理员配置。

## 8. Human 决策与升级后核验

- 升级 PR 按实际变更做风险评估；涉及依赖/工作流/Agent 安全规则/权限的
  按高风险处理。
- PR 仅在**当前 HEAD 对应**的必需检查与 Human 审查完成后合并。
- 合并后跑 `lacd status --json` 与 `lacd verify --strict`，确认锁/CLI/
  模板/远端强制符合目标版本；仅本地通过 → 保持 `VALIDATED`，不自动升 `ENFORCED`。
- 升级失败：Human 通过新 PR 或安全版本回退执行；不用危险的远端强制推送
  或改写历史做"回滚"。

## 9. 无中央登记数据库

采用状态存于采用者仓库内；CLI 从版本化清单与可验证的 GitHub 状态计算结果。
默认不上传采用者代码/秘密/仓库元数据给中央监控服务。集中统计若未来扩展，
必须是独立可选功能，不能是核心能力的前提。

## 10. 回退

- 每次迁移前备份到 `.lacd/backup/<timestamp>/`；`rollback_last()` 可恢复。
- 版本回退 = 一次受控的"降级迁移"（走同样的三方比较与 PR 流程），
  不允许以 force-push 改写历史实现。
